How this would actually work

Technical notes for the prototype above — pairing, sync, rules, scheduling.

QR pairing & local connection

The QR code printed on the lamp's base encodes a short pairing payload: a device identifier and a one-time pairing token, regenerated whenever the lamp is factory-reset. There's no cloud round-trip involved in the pairing handshake itself. Scanning the code with the companion app's camera decodes that payload and hands it to the phone's Bluetooth Low Energy stack, which the lamp advertises as a peripheral with a custom GATT service exposing a handful of characteristics: mode, variant, session_start, and ambient_lux.

The phone uses the token from the QR payload to complete a BLE bond (or, on lamps with a Wi-Fi radio, to join a Wi-Fi Direct group the lamp hosts) so future connections don't require rescanning. Once bonded, the app subscribes to notifications on the mode and variant characteristics — this subscription is what makes the rest of the sync work, since it lets the lamp push state changes to the phone instead of the phone having to poll. No account or internet connection is required for any of this; the QR code only ever needs to be scanned once per phone, and the link is local to the room.

Bidirectional mode sync

The lamp's firmware treats its own button presses as the single source of truth for hardware state. Pressing a physical button updates an internal state register immediately, regardless of whether a phone is connected, and the lamp's light output changes the instant the button is pressed — the app is never in the critical path for the lamp to function.

Whenever that internal register changes — whether from a button press or from a command the firmware received over BLE — the firmware writes the new value into the mode characteristic and emits a BLE notification. The app's only job on this path is to listen and re-render; it never assumes a button press implies a particular app state, it just reflects whatever the lamp reports. The flow in the prototype above is identical in both directions:

// firmware pseudocode onPhysicalButtonPress(btn) { state.mode = btn.mode; state.session_start = now(); ble.notify('mode', state.mode); // app updates from this } onAppCommand(cmd) { // identical handling — app command and button press // converge on the same state-mutation path state.mode = cmd.mode; state.session_start = now(); applyOutput(state); }

Because both triggers funnel into the same state mutation, there's no special-casing needed for "did the button or the app cause this" — the app simply mirrors whatever characteristic value it's notified of, which is exactly how the mock panel and the app body stay in lockstep in the prototype: pressing a mock button calls the same state setter the app's own mode cards call.

Rule system for sub-branches and variants

Each mode owns an ordered list of rules, evaluated top to bottom, where the first rule whose condition is true wins — the same first-match-wins shape used in the live trace panel above. A rule is just a predicate over a small context object (time of day, continuous session length, ambient lux, user-configured thresholds) paired with a variant descriptor (color warmth, brightness, and optional flags like blink).

// extensible rule shape { id, label, cond: (ctx) => boolean, variant: { warmth, brightness, blink? } }

This is deliberately not a hardcoded if/else chain specific to "screen" or "paper" — both modes consume the exact same evaluateRules(mode, ctx) function, so adding a third mode or a fifth sub-branch to an existing mode means appending a new rule object, not touching control flow. The break-reminder blink in screen mode is just a rule like any other: its condition checks sessionMins >= breakThresholdMins, and its variant carries a blink:true flag that a separate watcher checks for, firing a short flash sequence once per session and resetting only after the user changes mode (so it doesn't re-fire continuously while the condition stays true). The context object is intentionally small and flat so new signals — a presence sensor, a noise level, a calendar feed — can be added by extending ctx and writing a new rule, without changing how existing rules are evaluated.

Timeline engine: schedule-to-behavior mapping and overrides

The timeline is stored as a flat list of blocks, each with a start time, end time, and intended mode. A lightweight scheduler watches the clock and asks one question every time the clock crosses into a new block: "is there a block active right now, and if so, does the lamp's current mode already match it?" When the clock crosses into a new block's start time and no override is recorded for that block, the engine issues the same command-style state change described above — from the lamp's perspective, an automatic schedule transition looks identical to an app-issued command.

Overrides are tracked per-block rather than globally: if the user presses a physical button mid-block and the resulting mode doesn't match what that block calls for, the engine flags that specific block as overridden and stops trying to enforce its schedule for the remainder of its time window — it does not silently revert the lamp back to the scheduled mode, which is the behavior the prototype demonstrates with the dashed "overridden" block-row styling and the on-stage override tag. If the user later presses the button again to manually return to the block's original intended mode, the override flag clears, since at that point the lamp and the schedule agree again. The moment the clock crosses into the next block, the override flag is irrelevant anyway — each block gets a fresh chance to apply its schedule, which is why overrides are scoped to a single block's time window rather than persisting for the rest of the day.
